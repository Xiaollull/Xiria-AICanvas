模型

模型配置使用 models 下的项目相对路径，在 Windows 与 Linux 上均无需改动即可工作。每个根目录都可以使用自定义名称和任意嵌套。

模型目录

该目录沿用 ComfyUI 的模型分类命名，但完全由本项目自有。推理后端在两种操作系统上都相对项目根目录解析每一个配置路径。检查点、LoRA、放大模型、YOLO 检测器与兼容的背景移除模型会被递归扫描。

LoRA 根目录下的文件出现在 根目录 分类中；每个自定义的一级文件夹都会成为 UI 中的一个分类，更深层的文件夹仍会显示在模型名称里。移动或重命名已选模型会改变它的根相对 ID，因此整理文件后需要刷新并重新选择。

各根目录的内容

根目录内容
checkpoints/sdSD 1.x 或 SDXL 单文件检查点。.safetensors 支持 SDXL 检测；有歧义的 SD 2.x 与 SDXL .ckpt 文件目前不支持。
checkpoints/illustriousIllustrious / Illustrious XL 检查点。必须放在这里，才能选中正确的 SDXL 管道。
loras/sd、loras/illustriousLoRA 根目录。四个默认分类保持可用，同时自定义文件夹与任意嵌套会被自动发现。
vae分离式模型管道使用的独立与共享 VAE。
diffusion_modelsAnima、FLUX.1、FLUX.2、Krea 2 及其他分离式扩散权重。全部支持 .safetensors，其中三个引擎另支持 .gguf。
text_encoders分离式模型管道所需的独立文本编码器。
embeddings为将来的文本反转支持预留。
yolo用于本地 ADetailer 流程的 Ultralytics .pt 检测或分割模型。社区模型可以放在这里，包括放在子目录中。
background-removal兼容的 ONNX 前景提取模型。推荐文件即使被嵌套或改名，也按固定哈希识别。
upscalers重采样单元「超分模型放大」步骤使用的像素空间超分辨率权重（见后处理链）。兼容的 .pth、.pt、.ckpt 与 .safetensors 文件按张量结构发现，因此重命名文件不会改变兼容性。PyTorch 文件必须包含权重或 state dict；TorchScript 归档刻意不加载。
configs用户与模型的运行时配置产物。

原生 Anima 的 Qwen3 tokenizer、tokenizer config 与 T5 tokenizer JSON 文件随程序一并打包在 backend/resources/anima-tokenizers——它们是程序资源，而不是用户需要下载的模型。安装、启动与程序更新会自动校验打包的 tokenizer 字节，因此你只需下载 Anima DiT、文本编码器与 VAE。

ADetailer 检测在项目已验证的 Python 环境中以 CPU 运行。UI 会在下载官方模型前对 Hugging Face 与 hf-mirror 线路进行基准测试，并在 models/yolo 中续传被中断的下载。细节重绘保持在同一环境中，并继承当前的检查点、LoRA、采样器与调度器。模型文件绝不会被上传。

model-paths.json

程序更新会保留你自己的 models/model-paths.json，而不是覆盖它，因此自定义的模型根目录可以跨版本升级保留。未写出的键会回退到内置默认值，所以为旧版本编写的文件在新版本中依然正确。只有文件缺失、或更新后的项目无法使用该文件时，才会从发布包恢复默认副本。

推荐模型、YOLO 与背景移除目录则由每次更新刷新，因为那些是程序自带的清单，而非你的配置。

推荐模型浏览器

除你自己放入 models 的文件外，浏览器覆盖：

  • Illustrious —— WAI Illustrious SDXL、MiaoMiao Harem 与 Obsession Illustrious XL，各自跟踪其 Civitai 版本列表。
  • Anima —— CircleStone Labs 官方版本，同时来自 Civitai 与 Hugging Face 的 split_files 目录，并自动搭配共用的 Qwen 0.6B 文本编码器与 Qwen Image VAE。
  • FLUX.2 —— Klein 9B True V3 的 Safetensors 或 GGUF 版本，以及官方 Klein 9B KV 单文件版本（受限仓库，需接受许可并提供 Hugging Face Token）。两者都搭配 Qwen 3 8B 文本编码器与 FLUX.2 VAE。
  • Krea 2 —— 12B 模型的 Raw 与 Turbo 变体，并可单独选择 4B 文本编码器精度。其 VAE 与 Anima 共用。
  • 放大模型 —— 重采样单元在缩放与重绘之前可用来放大的 Real-ESRGAN 官方模型。
FLUX.2 的 fp8 文本编码器可以加载

官方发布的 fp8 版 Qwen 3 8B 有 141 层为 fp8、85 层为 nvfp4。两者都按 ComfyUI 的方式解码并在加载时展开，因此体积更小的文件是真正可用的选择；BF16 文件仍是全精度基准。详见下方的支持矩阵。

FLUX.1 没有推荐系列：它使用你自行准备的扩散模型、CLIP-L、T5-XXL 与 VAE 文件运行。

文件格式

所有组件都支持 .safetensors。FLUX.1、FLUX.2 与 Krea 2 的全部组件——扩散模型、文本编码器与 VAE——还支持 .gguf，某些量化版本只以这种形式发布。Anima 的组件仍然只接受 .safetensors。

GGUF 扩散模型与 VAE 保留检查点自身的张量命名（ComfyUI-GGUF 的写法），包括它对 ggml 无法容纳的 5 维卷积形状的记录。文本编码器多由 llama.cpp 发布，它会重命名每个张量；下表中的系列会被改回 ComfyUI 的命名，并且必须与文件声明的架构一致。其他情况按名称拒绝，而不是只加载一部分。

GGUF 文件会与 safetensors 文件一同出现在选择器中，并以同样的方式识别——依据文件内含的张量（llama.cpp 编码器还依据其声明的架构），而非文件名。

关于量化，说实话

发布方提供量化版本时也会一并列出，因此同一个模型可以选择 bf16、fp8、mxfp8、nvfp4、int4/int8 或 GGUF Q4-Q8。ComfyUI 的每种量化布局都按 ComfyUI 0.33.0 的方式读取——逐层 comfy_quant 标记或 _quantization_metadata 头部表、权重旁的缩放，以及权重在量化前是否经过旋转。运算直接移植自 ComfyUI 及其固定版本的 comfy-kitchen 0.2.31，而不是重新推导；许可与声明位于 backend/resources/comfy-quant。

布局Krea 2FLUX.1 / FLUX.2原生内核
FP8（float8_e4m3fn、float8_e5m2）保持 fp8，逐层解码加载时展开——
ConvRot INT8（int8_tensorwise + convrot）保持 int8；激活先旋转、逐行量化，再做整数矩阵乘——即 ComfyUI 的 W8A8 路径还原旋转后加载时展开INT8 张量核心，SM 7.5+
INT8（int8_tensorwise，逐张量或逐行）保持 int8，W8A8 整数矩阵乘加载时展开SM 7.5+

ConvRot W4A8（asym_w4a8_int8）、SVDQuant、ComfyUI-INT8-Fast 缺少 format 的标记按名称拒绝

标记了 full_precision_matrix_mult 的层，或被 LoRA 修改的层，会改为解码后以全精度相乘——这是 ComfyUI 自己的规则。在 SM 8.0 及以上的 NVIDIA 显卡上，两种整数矩阵乘由内置 Triton 内核完成：激活一次遍历完成量化，W4A4 的 4 位权重在寄存器中解包，结果与复现 comfy-kitchen eager 后端的 PyTorch 移植实现逐位一致。内核首次使用时先与移植实现比对，任何故障都会退回移植实现；没有 Triton 时直接运行移植实现。在 RTX 4060 上，一个 ConvRot INT8 的 Krea 2 块耗时 17 ms，BF16 为 40 ms，移植实现为 73 ms。已安装的 comfy-kitchen 会被优先使用，但程序从不自动安装它；设置 XIRAI_QUANT_TRITON=0 可关闭内置内核。每种布局在当前显卡上的执行路径会写在性能接口的 capabilities.quantization 中。

量化文件在内存中是否也更小，取决于引擎——取决于是否有一个线性算子可以接收它存储的权重。

引擎量化权重加载后的占用
Krea 2 就是它存储的大小，适用于上表中的每种布局。权重保持检查点自身的类型，缩放在线性算子内部完成，因此一个 fp8 扩散模型占用约 12 GB，而不是展开后的 24 GB——这正是能否常驻 24 GB 显卡的分界线——NVFP4 则约为 7 GB。
Anima、FLUX.1、FLUX.2 计算精度。它们通过键名转换挂载 Diffusers 的 transformer 类，缩放尚无路径穿过该转换，因此在加载时就被折算进权重，fp8 文件占用是磁盘体积的两倍。

对 fp8 而言，把缩放推迟到计算时并不是近似：对于权重仍是一个普通矩阵、只乘一个数的格式，它与在加载时折算得到的比特完全一致——这正是推迟它不需要付出代价的原因。被 LoRA 修改的量化层同样保持其存储形式，适配器挂在权重旁边，而不是融合进去。

GGUF 始终会展开

GGUF 的分块格式没有可以保留的计算时形态，因此无论哪个引擎读取它，都会在加载时展开为计算精度：Q4_K 文件的下载体积小得多，在内存中却与 bf16 一样大。那里的显存由显存模式与块级卸载决定，而不是由文件格式决定。

加载体积按张量形状及其存储类型计算，而非按文件大小计算，因此 Q4_K 模型按展开后的大小计入预算，fp8 的 Krea 2 模型则按它保持的大小计入。
